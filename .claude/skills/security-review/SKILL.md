# Security Review Skill

커밋 직전에 타입·취약점·시크릿 노출을 한 번에 훑고, 발견된 항목을 **위험도별로 분류**해 사용자 승인하에 처리한다.

근거: Refactor가 끝났어도 자동화 검사를 안 돌리면 *눈에 안 보이는 회귀* (오타로 인한 타입 에러, 새로 들어온 의존성의 CVE, 시크릿 키 하드코딩 등)가 커밋과 함께 묻혀 들어간다. 이 스킬은 그 게이트다.

---

## 입출력 계약

### 입력
- `$ARGUMENTS` — 이슈 번호 (예: `1`)
- 현재 작업 트리 상태 — `git status` 의 변경분 + 의존성 트리

### 산출물
- 발견된 항목의 **3등급 분류 보고**
- 사용자 승인 후 *즉시 수정 필요* 항목만 처리한 변경분
- 재스캔으로 확인된 **클린 상태** (또는 잔존 항목 명시)

---

## Security Review의 본질

> **"커밋하기 직전에 한 번만 깨끗하게."**

이 스킬은 *방어선*이지 *심사위원*이 아니다. 모든 경고를 다 잡으려 하면 노이즈로 둔감해진다. 그래서 **분류와 승인**이 핵심이다 — 즉시 처리할 것, 메모만 남길 것, 무시할 것을 명시적으로 갈라 사용자가 흐름을 잃지 않게 한다.

또한 자동 수정은 *안전한 것만*. `npm audit fix --force` 같은 메이저 버전 점프나 임의의 `any` 캐스팅 같은 우회는 새 회귀의 씨앗이다 — 절대 안 한다.

### 좋은 분류의 모양

| 등급 | 조건 | 예시 |
|------|------|------|
| 🔴 즉시 수정 | 빌드 실패 / 시크릿 노출 / 런타임 직격 / Critical·High CVE 중 직접 사용 경로 | `tsc` 에러, `.env`의 키가 코드에 하드코딩, 직접 의존성에 RCE |
| 🟡 권장 수정 | 빌드는 통과하지만 품질 저하 / 간접 의존성의 Moderate CVE / 비-prod 영향 | `any` 캐스팅 잔존, dev 의존성에만 영향 가는 CVE |
| ⚪ 무시 가능 | False positive / 의도된 패턴 / 업스트림 미배포 / 이번 이슈 범위 밖 | `db.json` 더미 토큰, 사용처 없는 의존성의 CVE |

### 나쁜 분류 (피해야 함)

- 모든 npm audit 결과를 🔴로 올림 → 즉시 처리 항목이 너무 많아져 게이트가 마비
- 모든 항목을 ⚪로 내림 → 게이트가 형식적
- 등급만 매기고 *근거*를 안 적음 → 다음 사이클에 같은 판단이 흔들림
- 사용자 승인 없이 자동 수정 → "왜 바뀌었지?" 가 PR에서 드러남

**원칙**: 등급마다 "왜 이 등급인지" 한 줄 근거를 적는다. 의심스러우면 한 단계 낮추고 사용자에게 묻는다.

---

## 절대 금지

- **`npm audit fix --force` 사용 금지** — 메이저 버전 자동 점프는 호환성 깨짐의 첫째 원인. 필요하면 사용자에게 보고하고 수동 결정.
- **테스트 파일 수정 금지** — `*.test.ts(x)`, `test-setup.ts` 모두 X. 타입 에러가 테스트 파일에 있으면 보고만 하고 사용자가 결정.
- **타입 에러 우회 금지** — `// @ts-ignore`, `// @ts-expect-error`, `as any`, `as unknown as ...` 자동 추가 X. 진짜 타입을 맞추는 게 원칙. 우회가 필요하면 보고하고 승인.
- **`.env` / `.env.*` / 비밀키가 들어있을 만한 파일 커밋·표시 금지** — 발견하면 *값을 마스킹해서* 보고한다. 전체 노출 X.
- **분류 등급 변경을 사용자 승인 없이 자동 적용 금지** — 보고 → 승인 → 처리 순서 엄수.
- **이번 이슈 범위 밖 파일 자동 수정 금지** — 발견은 보고하되, 처리는 별도 이슈로 분리 제안.

---

## 사전 확인

빠르게 점검 (없으면 사용자에게 보고):

- `package.json` 에 `typescript` + `vitest` 존재
- `tsconfig.json` 존재 (`strict` 옵션 권장)
- 작업 트리가 너무 더럽지 않은지 — 수십 개 미커밋 파일이 있으면 분리 권장
- `.gitignore` 에 `.env*` 가 포함되어 있는지

---

## 실행 순서

### 단계 1 — 타입 검사

```bash
npx tsc --noEmit
```

출력에서 다음을 수집:
- 파일경로 + 라인 + 컬럼
- 에러 코드 (예: `TS2322`)
- 메시지 한 줄
- *이번 이슈 diff 범위 내 파일인지* (단계 4 분류에 사용)

타임아웃·환경 문제로 실패하면 사용자에게 보고하고 중단. 추측으로 진행하지 않는다.

### 단계 2 — 의존성 취약점 스캔

```bash
npm audit --json
```

`--json` 으로 받아 다음을 추출:
- 패키지 이름 + 버전
- severity (`info` / `low` / `moderate` / `high` / `critical`)
- 직접 의존성인지 / 간접 의존성인지 (`isDirect`)
- prod / dev 구분
- 권장 조치 (`fixAvailable` 의 의미·범위)

> `npm audit` 는 같은 의존성이 여러 경로로 등장할 수 있으니 패키지 단위로 **묶어서** 본다. 같은 패키지의 같은 CVE를 N개로 세지 않는다.

### 단계 3 — 시크릿 노출 점검

#### 3-1. `.env` 파일 존재 + 무시 여부

- 레포 루트와 하위에 `.env` / `.env.*` 가 있는지 (있으면 `.gitignore` 매칭 확인)
- 추적된 적이 있는지: `git log --all --full-history -- .env .env.*` (있으면 *심각* — 히스토리 정리 필요 → 보고만, 자동 처리 X)

#### 3-2. `src/` 에서 비밀값 패턴 grep

`Grep` 도구로 `src/` 와 *non-test 파일*만 대상으로 다음을 검색:

| 패턴 | 의도 |
|------|------|
| `process.env.[A-Z_]+` | env 변수 직접 참조 — Vite 에선 보통 `import.meta.env` 를 쓰므로 노출 신호 |
| `import.meta.env.VITE_[A-Z_]+` | 클라이언트 번들에 노출됨 — public이 맞는지 확인 |
| `(api[_-]?key|secret|token|password|bearer)\s*[:=]\s*['"][^'"]{8,}` | 하드코딩된 시크릿 |
| `[A-Za-z0-9_-]{32,}` 가 *문자열 리터럴* 안에 단독 | base64 같은 토큰 패턴 |

**중요**: 매치된 라인을 그대로 보고서에 노출하지 않는다 — *값은 마스킹* (앞 4자 + `***`). 파일·줄 위치만 보여준다.

`db.json` / 픽스처 / 테스트는 검토 범위에서 제외 — 더미 데이터가 false positive 다수.

### 단계 4 — 3등급 분류 보고

수집한 모든 발견을 다음 형식으로:

```
## Security Review 결과 (이슈 N)

### 🔴 즉시 수정 필요
1. [타입 에러] src/components/NoteEditor.tsx:47 — TS2322 Type 'string' is not assignable to type 'string[]'
   - 근거: 빌드 차단. 이번 이슈 diff 안에 있음.
   - 조치 제안: 호출부에서 `tags` 인자에 배열을 넘기도록 수정.

2. [시크릿 노출] src/api/notes.ts:5 — `API_KEY = 'abcd***'` 하드코딩
   - 근거: 클라이언트 번들에 시크릿이 박혀 배포됨.
   - 조치 제안: `.env` 로 옮기고 `import.meta.env.VITE_API_KEY` 로 참조. `.env` 는 `.gitignore` 확인.

### 🟡 권장 수정
3. [취약점] lodash@4.17.20 — prototype pollution (Moderate, GHSA-xxxx)
   - 근거: dev 의존성 (`@testing-library` 경유). 런타임 영향 없음. fixAvailable.
   - 조치 제안: `npm install -D lodash@^4.17.21` (메이저 변경 없음). 후속 이슈로 분리해도 됨.

### ⚪ 무시 가능
4. [취약점] semver@5.x — ReDoS (High, GHSA-yyyy)
   - 근거: 간접 의존성, dev 트리에만 존재. fixAvailable 이 메이저 점프(7.x) 필요. 사용 경로 없음.
   - 조치 제안: 업스트림 패치 대기. 별도 메모만.

5. [grep] src/api/notes.ts:3 `import.meta.env.VITE_API_BASE_URL`
   - 근거: VITE_ prefix는 의도된 public env. 값도 URL이므로 정상.

### 요약
- 🔴 즉시 수정: 2건
- 🟡 권장: 1건
- ⚪ 무시: 2건

**진행 승인 요청드립니다.** 🔴 2건만 처리할까요? (🟡/⚪ 항목을 등급 조정하려면 알려주세요.)
```

> 보고는 *결과*뿐 아니라 *근거*가 핵심이다. 다음 사이클에서 같은 판단을 재현하려면 근거가 필요하다.

### 단계 5 — 승인된 항목만 처리

사용자가 🔴 목록을 승인하면 위에서부터 하나씩:

1. 변경 적용
2. 변경 직후 **해당 검사만** 빠르게 재실행:
   - 타입 에러였으면 `npx tsc --noEmit`
   - 시크릿 노출이었으면 단계 3-2 grep
3. 그 항목이 사라졌는지 확인
4. 다음 항목

원칙:
- 한 번에 한 항목. 묶지 않는다 — 회귀 원인 추적을 위해.
- `npm test` 도 마지막에 한 번 돌려 회귀 없음 확인.
- 타입 에러를 진짜 타입으로 해결하지 못하면 멈추고 보고. `as any` 자동 적용 금지.

🟡 / ⚪ 항목은 *건드리지 않는다*. 사용자가 명시적으로 "🟡도 처리해줘" 라고 하면 그것만 추가.

### 단계 6 — 재스캔 + 클린 상태 보고

전체 처리가 끝나면:

```bash
npx tsc --noEmit
npm audit
# + 단계 3-2 grep 재실행
npm test
```

기대 결과:
- 🔴 항목이 사라졌음
- 새로 생긴 🔴 항목 없음 (있으면 단계 4로 돌아감 — 회귀)
- 전체 테스트 통과 (Refactor 단계의 안전망 유지)

최종 보고:

```
## Security Review 완료 (이슈 N)

### 처리 결과
- 🔴 2건 모두 해소
  ✓ NoteEditor.tsx:47 타입 에러 — tags 인자 배열로 수정
  ✓ notes.ts API_KEY 하드코딩 — .env 로 이전 (.env.example 추가, .gitignore 확인)

### 잔존 항목 (의도적)
- 🟡 1건: lodash@4.17.20 — 후속 이슈 권장
- ⚪ 2건: 무시 (근거 위 보고 참조)

### 검사 상태
- tsc --noEmit: ✓ 에러 없음
- npm audit: 직접 의존성 critical/high 0건
- 시크릿 grep: 노출 없음
- npm test: 23/23 통과
```

이 보고가 커밋 메시지 본문 또는 PR 설명의 재료가 된다.

## 분류 가이드 — 자주 만나는 패턴

### 타입 에러

| 상황 | 등급 | 이유 |
|------|------|------|
| 이번 이슈 diff 내 src/ 파일에서 발생 | 🔴 | 빌드 차단 가능, 즉시 수정 |
| 다른 파일에서 발생 (이번 이슈와 무관) | 🟡 또는 ⚪ + 보고 | 이번 이슈 범위 밖 → 별도 이슈 분리 권장 |
| 테스트 파일에서 발생 | ⚪ + 보고만 | 스킬 제약상 자동 수정 금지 |

### npm audit

| 조건 | 등급 |
|------|------|
| Critical/High + 직접 의존성 + prod 트리 + fixAvailable | 🔴 |
| High/Moderate + 직접 의존성 + prod 트리 + 메이저 점프 필요 | 🟡 (사용자 결정) |
| High/Moderate + 간접 의존성 + dev 트리만 | 🟡 또는 ⚪ |
| Low/Info | ⚪ |

> `npm audit` 의 dev 트리 영향은 보통 빌드/테스트 도구에 한정. 그래도 *공급망 공격 표면*은 0이 아니므로 무조건 무시는 아님.

### .env / 시크릿

| 상황 | 등급 |
|------|------|
| src/ 코드에 시크릿 리터럴 하드코딩 | 🔴 |
| `.env*` 가 추적된 적 있음 (`git log` 결과) | 🔴 + 히스토리 정리는 보고만 |
| `import.meta.env.VITE_*` 사용 — public 의도 명확 | ⚪ |
| `process.env.*` 사용 (Vite 클라이언트 코드) | 🟡 — Vite에선 `import.meta.env` 권장 |

## 자주 하는 실수

- ❌ `npm audit fix --force` 한 방으로 끝내려 함 — 메이저 점프 회귀 위험. 절대 금지.
- ❌ 모든 항목을 🔴로 올려 처리 폭주 — 게이트 마비. 등급 의미가 사라짐.
- ❌ 타입 에러를 `as any` / `// @ts-ignore` 로 우회 — 진짜 타입을 맞추는 게 원칙.
- ❌ 시크릿을 발견 보고서에 *값 그대로* 노출 — 마스킹 필수.
- ❌ 사용자 승인 없이 자동 수정 — 등급 변경·수정 모두 승인 받고 진행.
- ❌ `.env` 가 *추적된 적 있다*는 것을 `.gitignore` 에 추가하면 끝났다고 생각 — 히스토리에 남아 있으면 이미 노출 (rotate 키 + 히스토리 정리 필요).
- ❌ 같은 패키지의 동일 CVE를 의존 트리 N번 등장한다고 N건으로 셈 — 묶어서 1건으로.
- ❌ 분류 근거를 안 적음 — 다음 사이클·다른 사람이 재현 불가.

---

## 끝맺음

🔴 0건 + 잔존 🟡/⚪ 항목의 *의도적 보류*가 명시되면 커밋 가능 상태다.

이 보고가 다음 단계(commit / PR 작성)의 입력이다. 커밋 메시지에 보안 점검 결과 요약을 함께 적어두면 다음 사람이 동일 영역을 검토할 때 비용이 준다.
