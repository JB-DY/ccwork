# 태그 기능 PRD

## 1. 개요

노트에 태그를 추가·삭제하고, 저장 시 서버에 함께 반영한다.
태그는 `Note` 객체에 `string[]`로 인라인 저장되며, NoteEditor에서 칩(chip) UI로 관리한다.

**제약 조건**: 노트당 최대 10개, 태그당 최대 20자. 공백 전용 입력 및 중복 태그는 무시된다.

---

## 2. 사용자 스토리

- 사용자로서, 노트 편집 화면에서 태그를 입력하고 Enter를 눌러 태그를 추가할 수 있다.
- 사용자로서, 추가된 태그를 칩 형태로 확인하고 `×` 버튼으로 즉시 제거할 수 있다.
- 사용자로서, 노트 저장 시 태그가 title·content와 함께 서버에 저장된다.
- 사용자로서, 중복 태그나 공백만 입력한 경우 추가되지 않아 목록이 오염되지 않는다.
- 사용자로서, 태그가 10개에 도달하면 더 이상 추가되지 않는다.
- 사용자로서, 20자를 초과하는 태그는 입력이 차단된다.

---

## 3. 기술 결정 (ADR)

### 3.1 태그 저장 시점

**Context** — 태그는 노트 편집 중 추가·삭제가 빈번하다. 변경할 때마다 서버에 저장하면 API 호출이 잦아지고, 편집 중 실수로 삭제한 태그도 즉시 반영된다. 반면 노트 저장 버튼과 함께 저장하면 기존 `title`/`content` 저장 흐름과 일관성을 유지할 수 있다.

**Decision** — 태그 변경은 로컬 상태에만 반영하고, 노트 저장 버튼 클릭 시 `title`·`content`·`tags`를 한 번에 서버에 전송한다.

**Alternatives**
- 안 A (태그 변경 즉시 저장 없음, 단 검증 로직을 NoteEditor에 직접 작성): 구조는 동일하나 검증 로직이 컴포넌트에 혼재 — ADR-3.3에서 별도 거부.
- 안 C (태그 변경 즉시 저장): 변경마다 `updateNote(id, { tags })` 호출. 저장 버튼 없이 반영되므로 UX가 명확하지 않고, 편집 중 네트워크 오류 처리가 복잡해진다. 기존 `saving` 상태 모델과도 불일치.

**Consequences**
- (+) 기존 저장 흐름과 완전히 동일 — Context·API 변경 없음
- (+) 저장 전 태그를 자유롭게 수정 가능 (실수 복구 가능)
- (-) 저장 버튼을 누르지 않으면 태그가 유실될 수 있음 — 향후 auto-save 도입 시 재검토 필요

---

### 3.2 중복 태그 비교 기준

**Context** — 사용자가 "React"와 "react"를 각각 입력했을 때 별개의 태그로 허용할지, 동일 태그로 간주할지 결정해야 한다. 허용하면 목록이 시각적으로 중복되어 혼란을 준다.

**Decision** — 중복 판정은 **대소문자 무시**(`toLowerCase()` 비교)로 처리하되, 저장값은 **입력 원본 그대로** 유지한다. ("React" 입력 후 "react" 재입력 시 무시, "React"가 유지됨)

**Alternatives**
- 대소문자 구분 허용: "React"와 "react"가 공존 가능. 태그가 시각적으로 중복되어 보여 사용자 혼란 유발.
- 모두 소문자로 정규화: 입력값을 항상 lowercase로 저장. 고유성은 보장되나 "TypeScript"처럼 대소문자가 의미 있는 태그의 표현을 훼손.

**Consequences**
- (+) 사용자 입력의 원본 표현(casing)을 보존
- (+) 중복으로 인한 혼란 방지
- (-) 첫 번째로 추가된 태그의 casing이 고정됨 — 추후 태그 편집 기능 추가 시 수정 필요

---

### 3.3 태그 상태 관리 위치

**Context** — 태그 추가·삭제·중복 검증·최대값 제한 로직을 어디에 둘지 결정해야 한다. NoteEditor 컴포넌트에 직접 넣으면 관심사가 혼재되고, Context에 넣으면 전역 상태가 과잉 확장된다.

**Decision** — `src/hooks/useTagInput.ts` 커스텀 훅으로 분리한다. 훅은 `initialTags`를 받아 `{ tags, addTag, removeTag, reset }`을 반환하며, 모든 검증 로직(trim, 중복, 최대 10개, 최대 20자)을 내부에서 처리한다. NoteEditor는 훅만 호출하고 저장 시 `tags`를 `updateNote`에 전달한다. `reset`은 선택된 노트가 바뀔 때(`selectedNoteId` 변경) 호출해 이전 태그 상태를 초기화한다.

**Alternatives**
- 안 A (NoteEditor 로컬 state 직접 관리): 구현이 단순하나 검증 로직이 컴포넌트에 혼재되어 단위 테스트가 어렵고, 재사용 불가.
- 안 C (Context 레벨 액션): `addTag(noteId, tag)` / `removeTag(noteId, tag)`를 Context에 추가. 태그 변경마다 API 호출이 필요해 저장 시점 결정(ADR-3.1)과 충돌. Context가 불필요하게 비대해짐.

**Consequences**
- (+) 검증 로직을 훅 단독으로 단위 테스트 가능 (컴포넌트 렌더링 불필요)
- (+) Context·API 변경 없이 기존 패턴 유지
- (+) 향후 다른 컴포넌트에서 태그 입력이 필요할 때 훅 재사용 가능
- (-) 파일이 1개 추가됨 (`hooks/useTagInput.ts`)

---

## 4. Out of Scope

이 버전은 NoteEditor 내 태그 추가·삭제·저장에만 집중한다.

### v1 이후 고려 가능

| 항목 | 제외 이유 |
|------|-----------|
| 태그 기반 필터링 / 검색 | NoteList 전체 쿼리 로직 필요 — 별도 이슈로 분리 |
| 태그 자동완성 | 전체 태그 목록 집계 필요 — Context 확장 동반 |
| NoteItem 태그 미리보기 | 편집 화면 집중, 리스트 UI 복잡도 증가 방지 |
| 태그 인라인 편집 | 삭제 후 재입력으로 대체 가능, 복잡도 대비 가치 낮음 |

### 의도적으로 제외 (설계 경계)

| 항목 | 이유 |
|------|------|
| 태그 전역 관리 (일괄 변경·삭제) | 별도 태그 엔터티 도입 필요 — 현재 인라인 `string[]` 구조와 충돌 |
| 태그 계층 구조 (부모/자식) | 플랫 `string[]` 구조로 충분, 과잉 설계 |
| 태그 색상 커스터마이징 | 디자인 시스템 Chip 토큰 외 커스텀 색상 금지 |
| 태그 정렬 | 입력 순서 유지가 사용자 의도를 반영 |
| 태그 드래그 앤 드롭 순서 변경 | 정렬 기능 자체가 제외 범위 |

---

## 5. 용어 정의

| 용어 | 정의 |
|------|------|
| 태그(Tag) | 노트에 붙이는 문자열 레이블. 노트당 최대 10개, 태그당 최대 20자 |
| 칩(Chip) | 태그를 시각적으로 표현하는 UI 요소. `×` 버튼 포함 |
| 인라인 저장 | 별도 태그 테이블 없이 `Note` 객체의 `tags: string[]` 필드에 직접 저장 |
| 중복 태그 | 대소문자 구분 없이 동일한 문자열. 추가 시 무시되며 저장값은 입력 원본 그대로 유지 |
| `useTagInput` | 태그 상태·검증 로직을 캡슐화한 커스텀 훅 (`src/hooks/useTagInput.ts`). `{ tags, addTag, removeTag, reset }` 반환 |
